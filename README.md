# Практика 7. Ввод-вывод и файлы

```
javac -d out $(find src -name "*.java")
```

```

```

java -Xmx16m -cp out Task8StreamingImport

## Ответы

### 1. `Files.readString / writeString`

Кодировка всегда указана явно: `StandardCharsets.UTF_8`. `load` не перехватывает ошибки:
нет файла — летит `NoSuchFileException`, вместо файла каталог — `IOException` с понятным сообщением
(проверка `Files.isDirectory` сделана явно, потому что текст системной ошибки зависит от ОС).

Плохо было бы так: `catch (IOException e) { e.printStackTrace(); return List.of(); }` —
вызывающий получает пустой каталог и думает, что всё прочитано (ложный успех).
В `main` ошибки ловятся только на верхнем уровне, чтобы показать сообщение, и программа явно пишет «каталог НЕ загружен».

Вывод: файл 136 байт, но 93 символа — кириллица в UTF-8 занимает 2 байта на букву.

### 2. `Reader / Writer`

Цепочка: `InputStream` (байты) → `InputStreamReader` с `Charset` (декодирование) → `BufferedReader` (буфер + `readLine`).
Запись в обратную сторону: `BufferedWriter` → `OutputStreamWriter` (кодирование) → `OutputStream`.

Граница bytes → chars проходит ровно в `InputStreamReader` / `OutputStreamWriter`: только здесь применяется кодировка.
Всё, что ниже — байты, всё, что выше — `char`. Если на этой границе указать не ту кодировку,
данные испортятся без всякой ошибки: тот же файл в ISO-8859-1 даёт 133 символа вместо 90 (каждый байт стал «символом»).
Количество символов ≠ количество байт: `"Ёж"` — 2 `char`, 4 байта в UTF-8.

`readLine` отрезает перевод строки, поэтому символы считаются без `\n`.

### 3. Try-with-resources

Reader и writer объявлены в одном `try (...)`. На третьей строке выбрасывается исключение. Лог:

```
открыт reader → открыт writer → записаны 1, 2 → исключение → закрыт writer → закрыт reader → catch
```

- оба ресурса закрыты (флаги `closed = true`);
- порядок закрытия обратный порядку открытия (сначала writer, потом reader);
- ресурсы закрываются до входа в `catch`;
- `close()` у `BufferedWriter` делает `flush`, поэтому уже записанные строки попали в файл.

Если бы `close()` тоже бросил исключение, оно не потеряло бы основное, а добавилось бы в `getSuppressed()`.

### 4. Ленивые строки

`Files.lines` возвращает ленивый `Stream`, за которым стоит открытый файл. Строки читаются только во время терминальной операции.

- `countByPrefix` — правильно: stream открыт и закрыт в одном методе.
- `brokenLines` — ошибка: stream возвращается из `try`, и `try` его тут же закрывает. Вызывающий получает
  `IllegalStateException: stream has already been operated upon or closed`.
- `openLines` без `try` у вызывающего — ошибка: `count()` отработал, но `onClose` не вызван, файл остался открыт (утечка дескриптора).

Владеть ресурсом обязан тот, кто последним его использует. Либо метод сам открывает и закрывает stream и
возвращает готовый результат (число, `List`), либо метод отдаёт stream наружу и тогда вызывающий обязан закрыть его
своим `try-with-resources` (вариант 4, `onClose` срабатывает).

### 5. Бинарный формат

```
int    magic   = 0x43525331 ("CRS1")
short  version = 1
int    count
count × { UTF code, UTF title, int hours }
```

Чтение через `DataInputStream`:
- чужой magic → «Неизвестный заголовок» (так отклоняется, например, текстовый файл);
- версия не 1 → «Неподдерживаемая версия»;
- файл кончился раньше времени → `readInt/readUTF` бросают `EOFException`, который превращается в `CatalogFormatException("Файл обрезан")`;
- лишние байты после записей и некорректные значения полей тоже отклоняются.

### 6. Временный файл и move

1. `Files.createTempFile(тот же каталог, ...)` — тот же каталог нужен, чтобы move был переименованием на одной файловой системе (между ФС атомарного move не бывает).
2. Запись в temp, `flush`, `close` (через try-with-resources).
3. `Files.move(temp, target, ATOMIC_MOVE, REPLACE_EXISTING)` — читатели видят либо старый, либо новый файл целиком.
4. Если ФС бросает `AtomicMoveNotSupportedException` — повторяем `move` без `ATOMIC_MOVE` и возвращаем `SaveMode.NON_ATOMIC`, чтобы вызывающий знал, что гарантии атомарности нет.
5. `finally { deleteIfExists(temp) }` — при любом сбое временный файл не остаётся.

Чтобы показать пункт 4 на обычной ФС, `move` передаётся интерфейсом `Mover`, и в демо подставляется вариант, который не умеет `ATOMIC_MOVE`.
Демо 3: сбой во время записи временного файла — целевой файл остался прежним, `.tmp` удалён.

### 7. Частично повреждённый импорт

Выбран контракт **atomic all-or-nothing**. Он закреплён типом:

```java
sealed interface ImportResult {
    record Success(List<Course> courses) implements ImportResult {}
    record Failure(List<ImportError> errors) implements ImportResult {}
}
```

Импортёр проходит весь файл и собирает **все** ошибки с номерами строк (`ImportError(line, message)`),
но курсы возвращает только если ошибок нет. У `Failure` нет списка курсов вообще, поэтому опубликовать половину каталога
невозможно даже по ошибке. `switch` по sealed-интерфейсу заставляет обработать оба случая.
Ошибка чтения файла (`IOException`) — это не ошибка данных, она пробрасывается дальше.

### 8. Потоковый импорт большого файла

Файл читается построчно через `BufferedReader.readLine()`, в памяти одновременно только одна строка.
Курсы не накапливаются — считаются только счётчики (строк, импортировано, ошибок, сумма часов).

- список ошибок ограничен `maxStoredErrors` (хранятся первые N, остальные только считаются);
- при достижении `failLimit` ошибок импорт прерывается и в отчёте `cancelled = true`.

Проверка: файл 278 МБ, куча `-Xmx16m` — всё прошло. С `readAllLines` был бы `OutOfMemoryError`.

### 9. Версионируемый формат

Версия 2:

```
int magic, short version = 2, int count,
int payloadLength, long crc32(payload),
payload = count × { UTF code, UTF title, int hours }
```

- **Schema version** — поле `version` после magic. Читатель делает `switch`: 1 и 2 знает, любая другая — исключение.
  Будущая версия 3 не читается «как старая». Старый читатель из задания 5 тоже честно отказывается читать v2.
- **Checksum** — CRC32 от payload. Payload сначала читается целиком в `byte[]`, проверяется checksum,
  и только потом из него создаются объекты `Course`. Повреждённый файл отклоняется до публикации — в демо опубликованный каталог остаётся прежним.
- **Migration 1 → 2** — `migrateToV2` читает v1 (формат задания 5) и перезаписывает файл в v2 через temp + move из задания 6, так что
  при сбое миграции старый файл не теряется.
